Build or control a Grin node

How Script 01 installs a Grin node from a chain snapshot, what each wizard choice means, and how to start, stop, update or rebuild a node from its menu.

Covers the toolkit as of 23 Oct 2026Page updated 24 Oct 2026Toolkit on GitHub

Script 01 is the foundation of the toolkit: it puts a synced Grin node on the server, and every other script builds on that node. It is also where you come back to start, stop or update a node, or to rebuild a corrupted one.

Note

Status — Script 01's menu was rebuilt in October 2026: one status screen with numbered keys for each node action. The new menu has been tested against a simulated server only, not yet on a real VPS. If a screen differs from this page, the script's own text is the one to trust.

What it does#

An ordinary Grin install syncs the chain from genesis over the peer network. That takes hours to days and, with the current PIBD (Parallel Initial Block Download) mechanism, sometimes stalls or loops. Script 01 avoids all of it:

  1. Downloads the latest official grin release (linux-x86_64) from GitHub. The release binary is not checksum-checked; the chain snapshot in full download mode is.
  2. Generates the node configuration with grin's own server config command, then patches in the toolkit's standard paths and your choices.
  3. Downloads a pre-synced chain snapshot from a community host, checking that the snapshot is fresh, and extracts it into the node directory.
  4. Starts the node as the unprivileged grin user inside a tmux session, adds a Tor .onion address for its API, and re-points any already-installed services at the new node.

The result is a node at the current chain height within the time it takes to download a few gigabytes. Every build then offers autostart on reboot and the node event recorder; Super Auto turns both on without asking and adds a sync watchdog and log rotation.

Choices you will make#

Whichever menu key you use, these are the decisions behind it. Read them once and the prompts make sense.

Network: mainnet, testnet or both#

Mainnet is the real Grin network. Testnet is a separate chain of worthless test coins, useful for rehearsing wallet and mining setups. A server can host at most one node per network. Choosing Both builds mainnet first, then testnet, each in its own directory with its own copy of the binary. The install only offers networks that have no node yet.

Mode: pruned or full archive#

PrunedFull archive
KeepsThe full header chain and every kernel; block bodies only for recent blocksEverything since genesis
Disk neededAbout 10 GB free (a few GB of chain data plus room to grow)25 GB free and growing
Good forRunning a node, wallets, mining, the public API, the stats dashboardServing old blocks: the GrinScan explorer, sharing full snapshots
Available onMainnet and testnetMainnet only

Pruned is the default and the right choice unless you know you need old block bodies. A pruned node is a fully validating node: it verifies every block, it just does not keep all of them. The two modes use different directories (mainnet-prune and mainnet-full); building one mainnet mode removes the other mode's directory.

Chain data source#

OptionWhat happensWhen to use it
On-the-fly (default)Streams the snapshot from the host straight into tar. Nothing is stored beside the extracted data, and the script switches host automatically if the download breaks. No SHA256 check in this modeAlmost always: it is the fastest and needs the least disk
Full downloadSaves the .tar.gz to disk first (resumable), verifies its SHA256, checks free space, then extractsWhen your connection is unreliable and you want a resumable, checksum-verified download
Slow syncNo snapshot at all. The node starts with an empty chain_data/ and syncs from genesis over P2P, exactly as a stock Grin install wouldOnly when no snapshot host is fresh or reachable. Takes hours to days

For the first two options you also pick a download zone: America, Asia, Europe, Africa, or Auto (every zone at once). The script loads the community host list from extensions/grinmasternodes.json, shuffles the zone's hosts to spread the load, and probes each one for a snapshot that is recent enough (5 days for a pruned snapshot, 70 days for a full archive). It downloads from the first host that passes and keeps the others as fallbacks; the menu says "fastest", but hosts are not ranked by speed or age. A zone with no hosts listed uses America's list. If none of the zone's hosts is fresh, the script tries every zone; if that fails too, it asks for a custom URL or 0 to go back.

Note

The snapshot is a convenience, not a trust decision you are stuck with. The node validates the data it receives from peers from that point on; a bad snapshot would simply fail to sync. Once your own node is synced you can share your own snapshot with Script 03 and become one of the hosts.

Super Auto#

Super Auto is the answer to "just give me a working node". One key, one confirmation, and both networks are built and hardened. It will:

  • Build mainnet-prune and testnet-prune with the chain snapshot streamed on-the-fly from a fresh host in any zone.
  • Enable autostart on reboot (a crontab @reboot entry: mainnet starts 5 seconds after boot, testnet 1000 seconds later so they never compete for the disk).
  • Install the sync watchdog, a cron job every 5 minutes that restarts a node that is down, or whose height has stopped advancing while public height references keep moving. Its default config watches mainnet only: testnet is listed but disabled in /opt/grin/conf/grin_node_watchdog.json.
  • Install the node event recorder, a read-only timer (every 30 seconds) that logs each time a node goes down or comes back and saves its console and logs at the moment of failure. It never restarts anything. View it in Admin & Maintenance → Diagnostics → Node event recorder.
  • Set up log rotation for each grin-server.log (/etc/logrotate.d/grin-node-<network>: rotated once it passes 50 MB, seven compressed copies kept).
  • Add a Tor .onion address for each node's API (see step 13b).

It wants 20 GB free on the filesystem holding /opt/grin/node. With less it warns and asks you to type FORCE to go ahead anyway.

Danger

Super Auto is destructive on a server that already has a node. It stops every Grin node and deletes the binaries and chain_data of both networks before rebuilding, and it only ever builds pruned nodes, so a full archive would be gone. It lists what it will remove (version, chain size, date) and asks you to type REBUILD, or DELETE-ARCHIVE when a full archive is among them. On an empty server it asks a plain Proceed? [Y/n]. Wallets are not touched, but if you have anything on the box you are not sure about, use 5 (install) or 4 (rebuild one network) instead.

Warning

Super Auto looks for a legacy ~/.grin directory only after the wipe. If it finds one, answer D (delete) or Enter (keep): 0 there goes back to the menu with the old nodes already deleted and nothing rebuilt.

The custom wizard, step by step#

Key 5 (install) and the full reinstall under key 4 run the wizard, a pipeline of numbered steps. It prints each step's header as it goes, so you can follow along. At most prompts 0 goes back to the Script 01 menu.

With Both selected, steps 4–14d run for mainnet, then straight away for testnet. There is no pause between the two builds, so on a small VPS the testnet node can start while mainnet is still booting.

Warning

A full reinstall (and Super Auto) regenerates grin-server.toml from scratch. If you mine solo on this node, the stratum settings that Script 07 added are gone afterwards: run its setup again. A public pool's stratum settings are written back into the config by grin-secret-sync (step 14b, then every 5 minutes), but only after the node has already started, so the pool's stratum stays off until you restart the node: Script 01 → 2 Stop a node, then 1 Start a node.

Compile from source (key G)#

G opens its own menu for running a grin binary you compiled yourself. Use it when a fix is on grin's staging branch but not in a release yet, when your system's glibc is too old for the release binary, or to go back to the previous binary after an update.

  1) Compile a branch/tag into a binary   (default: staging)
  2) Install a local compiled binary into the node(s) already installed
     replaces <node_dir>/grin, keeps grin.prev, restarts the node
  3) Install a local compiled binary into the NEXT node you build
     for a node that does not exist yet — Step 6 uses it instead of
     downloading the GitHub release. Applies to this run only.
  4) Roll back — restore <node_dir>/grin.prev
  5) Purge the cargo build cache  (frees several GB)
  0) Back
KeyWhat it does
1Asks for a git ref (branch, tag or commit; Enter = staging), checks disk and memory, installs the build tools and Rust if missing, checks out /opt/grin/src/grin and runs cargo build --release. The result is kept in /opt/grin/bin/. Then offers 2 or 3
2Installs a binary from /opt/grin/bin/ into the installed node(s), keeping the old one as <node_dir>/grin.prev plus an archived copy in /opt/grin/bin/, then starts the node(s)
3Meant to arm the binary for the next install (key 5, 4 full reinstall or A) in this Script 01 session, instead of the GitHub download. It does not carry over at the moment: see the known problem below
4Puts grin.prev back
5Deletes the cargo target/ cache. The next compile then takes much longer

After the checkout, 1 offers the toolkit's grin patches (scripts/patches/grin/ in the toolkit): fixes the toolkit carries until grin ships its own. At the time of writing they speed up the daily chain compaction that can freeze an archive node's API for hours, and log how long each compaction took. They are applied all-or-nothing; if one does not fit the chosen ref you can build plain upstream instead. A patched binary's name contains -tkp<N>- so it never passes for a release.

Warning

A compile takes 20–45 minutes and needs about 5 GB of disk and 3 GB of RAM plus swap; the script warns below that and offers to add swap. Run it inside tmux new -s grinbuild, because a dropped SSH session kills the build. The patched build has not been compiled on a VPS yet.

Note

2 and 4 stop every running node, then start only the nodes they changed, with no pause between mainnet and testnet. 2 changes every installed node, so a node that was stopped before is started too. 4 changes only nodes that have a grin.prev: a node without one is stopped and left stopped, so start it again with Script 01 → 1. A rollback uses up grin.prev, so a second 4 has nothing to restore.

Warning

Known problem, read from the code: 3 (and the 3 offered after a compile) does not survive leaving the G menu. The menu runs each action in a separate process, so the armed binary is forgotten when you go back to the Script 01 menu, and the next install downloads the GitHub release as usual. Until this is fixed, build the node normally, then use G → 2 to swap in your compiled binary.

After it finishes#

Give the node a few minutes: a Grin node loads its chain into memory at start-up before it opens its ports and accepts peers. Then check it.

gtmux ls                                   # the node session(s)
gtmux attach -t grin_pruned_mainnet        # live output; Ctrl+B then D to detach
tail -f /opt/grin/node/mainnet-prune/grin-server.log

A healthy node's log shows the tip height advancing every minute or so and a stable count of peers. A JSON status check that does not need tmux:

cd /opt/grin/node/mainnet-prune
curl -s -u "grin:$(cat .api_secret)" -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"get_status","params":[],"id":1}' \
  http://127.0.0.1:3413/v2/owner

Look for "sync_status":"no_sync" (grin's way of saying synced) and a height close to what a public explorer shows. For testnet use testnet-prune and port 13413. Admin & Maintenance → Node Status & Sync prints the same for every node.

Make sure inbound 3414 (mainnet) and 13414 (testnet) are open in your provider's firewall or security group, otherwise other nodes cannot reach yours and you only make outbound connections.

If you did not use Super Auto#

The wizard offers autostart on reboot (step 14c) and the event recorder (step 14d). If you declined, add autostart later from Script 03 → key G (Auto startup Grin node). The sync watchdog is installed from the mining hub, Script 07 → Solo mining → Watchdogs, because it grew out of the solo-mining health checks; it protects any toolkit node, mining or not. Log rotation for grin-server.log is only set up by Super Auto.

Troubleshooting#

SymptomCause and fix
version 'GLIBC_2.38' not found right after the buildThe distribution is too old for the release binary. Reinstall on Ubuntu 24.04, or compile with G. Do not upgrade glibc by hand; see Getting started
lock file is held by another grin processTwo copies of grin are pointed at the same chain_data, usually a node started by hand as root next to the toolkit's. Script 01 → 2 stops that network's node on both tmux servers, then 1 starts the right one
Error loading config file: Permission denied or the node exits at once after a manual startFiles in the node directory are owned by root because the node was once run as root. Start it from the menu (1): the launcher fixes ownership and runs it as grin
Not available now: … after pressing a keyThe key cannot act in the current state, for example 5 when both networks are installed, or 1 when every node already runs. The reason is the dim text on that key's row
cannot start — repair with 4) Rebuild a nodeThe node directory lost its grin binary or grin-server.toml. Use 4 → that network → full reinstall; the API secrets and .onion identity are kept

Insufficient disk space in step 5, or the check fails in step 11Free space, or choose pruned instead of full. Old archives in /opt/grin/node/*/ and apt clean are the usual quick wins; Admin & Maintenance → Disk cleanup does it from the menu
Another instance of script 01 is already runningScript 01 is open in another SSH session. Finish or close that one. If none exists, remove /var/run/grin-toolkit-01.lock

Height stops advancingWait ten minutes first: a node occasionally pauses while it verifies a batch. If it stays stuck, 4 → chain_data only rebuilds the chain data from a fresh snapshot
