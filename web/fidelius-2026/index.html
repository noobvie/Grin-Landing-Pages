Grin Personal Web Wallet Self-hosted · Issue 2026

Your wallet lives on a machine you own, and opens in any browser.

Fidelius is a browser front end for the official grin-wallet, installed on your own server by one script. There is no app to install, no store to be approved by, and no account anywhere. Reach it over public HTTPS behind a password — or seal it inside a WireGuard tunnel where the internet cannot find it at all.

The instrument

A front end, not a new wallet.

Fidelius writes no cryptography of its own. It drives the wallet the Grin project publishes, on hardware you chose, and gives it a screen you can reach from anywhere.

Upstream

The official binary does the work

Fidelius downloads grin-wallet from the mimblewimble release page, verifies its SHA256, and pins it at v5.4.1. It then talks to it over the Owner API v3 — ECDH key exchange, AES-256-GCM on every call. Your keys are handled by the same code a command-line user runs.

Shape

One service, many wallets

A single Node process on 127.0.0.1:7420 under systemd, with nginx in front holding TLS and the password. It serves as many wallets as you create, mainnet and testnet side by side, each in its own directory with its own seed.

Secrets

The passphrase never touches disk

It is passed to grin-wallet over stdin — never on a command line, where every local user could read it in ps — and held in process memory only while the wallet is unlocked. The browser locks on idle, and a server-side backstop locks it again if you simply close the tab.

Neighbours

Beside your own node

The same toolkit installs the Grin node. Point Fidelius at it and nothing about your balance, your addresses or your broadcasts passes through a stranger’s server. Public nodes are offered as a fallback, not a default requirement.

Reach

Two doors, and you pick

Public HTTPS with Basic Auth, rate limits and a fail2ban jail on failed logins — or the private path, where nginx listens only on a WireGuard address and the wallet has no public surface at all. Switching between them is a menu option, not a rebuild.

Backups

Seeds included in the archive

The toolkit’s encrypted backup finds Fidelius wallets by looking at what actually exists on disk, so a wallet you create next month is covered without re-running anything. Restore puts the seeds and the registry back where the service expects them.

Transport

Three ways to hand over a payment.

Grin has no addresses that simply receive. A payment is a short conversation between two wallets, so the interesting question is always: how does the other side hear from you?

Choosing a rail
Rail Both online? You copy a blob? Use it when
Tor Required No The payee runs a wallet that is listening now. Fastest, and the only rail that finishes in one click.
Slatepack No Yes — three rounds You have any channel to the other person at all: email, a messenger, a printed QR. Nothing else has to exist.
Transporter No No Neither of you keeps a wallet online. An encrypted queue holds the slate until the other wallet next unlocks.
Rail 1 · Tor

Straight through, nothing to carry

Your wallet dials the recipient’s onion address and completes the exchange itself. Because Fidelius lives on a server that is always on, your own listener is reachable while every device you own is switched off — people can pay you in your sleep.

Rail 2 · Slatepack

A block of text, sent however you like

The wallet gives you an armored block. They receive it, hand one back, you finalize. It works with no relay, no Tor and no shared uptime — and it is the rail you fall back on when everything else is having a bad day.

Rail 3 · Transporter

A queue that waits for them

The slate is encrypted to the recipient’s key and deposited into a store-and-forward queue you or someone you trust runs. The relay can refuse to deliver and can see which address talks to which — it can never read the slate or spend from it.

The one failure worth memorising. A Transporter deposit to a well-formed but wrong address succeeds. It lands in a queue nobody owns, no error is ever raised, and the only symptom is coins that stay reserved forever. Send 0.1 ∩ first, wait for it to complete, then send the rest. Fidelius prompts you to do exactly that on any first payment to an unknown address.

Position

What a server wallet gives you that a phone wallet can’t.

Grim and Goblin are good wallets, and this is not an argument that they are wrong. They are a different shape of tool: an app on a device you carry. Fidelius is a service on a machine that never sleeps. The trade runs in both directions.

Advantage

It is a URL, so it goes where you go

A borrowed laptop, a work machine you may not install software on, a tablet, a phone whose store has no Grin wallet at all. The wallet does not have to be ported to a platform to be reachable from it — and there is no wallet app sitting on the device afterwards.

Advantage

Open at the front, or invisible

Run it publicly behind TLS, a password and a ban jail. Or take the private path: nginx binds to a WireGuard address only, and the wallet stops existing for everyone who is not inside your tunnel — while keeping a real, publicly-trusted certificate. Same install, one menu option apart.

Advantage

No new cryptography to trust

Every key operation is the official grin-wallet binary that the Grin project releases, pinned to a version this project has read, and checksum-verified on download. What Fidelius adds is a screen, a session, and three ways to deliver a slate.

Use Grim or Goblin instead when you don’t want to run a server — that is the honest dividing line. They start in minutes with nothing to rent and nothing to maintain, your keys stay on hardware you physically hold, and Goblin’s pay-by-username over Nostr is genuinely nicer than copying addresses around. If you already run a node, Fidelius costs you nothing new. If you don’t, a device wallet is the smaller, saner tool.

Guards

What actually stands between a stranger and your coins.

Stated as layers, so you can see where each one stops and what it never covered.

Defence layers
LayerWhat it doesWhat it does not do
nginx TLS, Basic Auth on every path, strict CSP with no inline script, rate limits on sending and on the API, security headers, a 1 MB body cap. It cannot help once someone knows the password.
fail2ban Bans an address after repeated failed logins. Basic Auth is the whole authentication boundary, so this is the thing that makes guessing expensive. Nothing against a leaked or reused password.
The session The passphrase lives in process memory while unlocked. The browser locks on real idle time, and a server-side timer locks it again if you close the tab. Background pollers deliberately do not count as activity. An unlocked session in front of someone else is an unlocked wallet.
grin-wallet Holds the seed, signs, builds transactions. Reached over Owner API v3: ECDH key exchange, AES-256-GCM per call. The passphrase is fed on stdin, never on a command line. It cannot recover a lost passphrase. Nobody can.
systemd ProtectSystem=full, ProtectHome=true, PrivateTmp=true, NoNewPrivileges=true, and one writable path. The service runs as root; the sandbox narrows the blast radius, it does not remove it.
WireGuard (optional) Removes the wallet from the public internet entirely — see below. Changes who can reach it, never what happens once they do.

Private access

A real certificate, and no open port.

The usual trade is that a private service gets a self-signed certificate and a browser warning you learn to click through. This avoids the trade: the certificate is issued by proving control of the domain through DNS, which never connects to your server at all.

your phone→ udp/51820→ wg0 · 10.9.0.1→ nginx listens 10.9.0.1:443→ 127.0.0.1:7420
Why it works

DNS-01 never dials your host

Let’s Encrypt asks for a TXT record instead of an HTTP request, so issuance and renewal both work with every port closed. Your public DNS record then points a public name at a private address — and only a device inside the tunnel can route to it.

Why bind, not block

An address nginx never listens on cannot be probed

An allow/deny rule still lets a stranger complete the TLS handshake and reach the HTTP layer before being refused — so any pre-authentication bug stays reachable, and the host stays confirmable. Binding to the tunnel address removes the surface instead of guarding it.

Two locked doors

It refuses to lock you out

The switch will not run until a device has actually completed a handshake — a config file is not evidence — and it refuses to proceed on a certificate whose renewal needs port 80, because that one renews fine today and fails silently two months later.

Say the quiet part. A tunnel changes who can reach the wallet, not what happens after they do. The service still runs as root, and a stolen device that is already inside the tunnel is a complete bypass. Private access is a way to shrink the audience — it is not a second password.

Terms

What this costs you, before you install it.

Every clause below is a plain fact about how the software is built. None of them can be fixed by a support ticket, because there is nobody to open one with.

The passphrase is arithmetic, not policy

It is not stored anywhere — not in a database, not on the server, not with anyone. There is no reset link and no override, because there is nothing to override. Forget it and the coins in that wallet are gone, permanently.

The recovery phrase is shown once

Twenty-four words, at creation. Write them on paper and store the paper somewhere a fire or a burglary would not take with it. A screenshot puts your wallet in your photo library, and eventually in whatever backs that library up.

Your server operator is inside your trust boundary

The seeds sit on that machine. Anyone with root on it — you, an intruder, or the company you rent it from — can reach them. A rented VPS is convenient; it is not the same as hardware you physically hold, and it is not a backup.

A browser is a wider door than an app

The wallet is reachable by anyone who has your password and can reach the address. That is the deal you accept in exchange for it working everywhere. Use a password you use nowhere else, install the ban jail, and consider the private path if the wallet holds anything that matters.

It is in testing, and the version is deliberately frozen

The code is complete and has been reviewed, but has not been proven on a live production server. grin-wallet is pinned to v5.4.1 on purpose: the way Fidelius hands over a passphrase depends on how that version reads input, so upgrades are made by a human who has checked, never by chasing the latest release.

Installation

Self-hosting it, start to finish.

Fidelius ships inside the Grin Node Toolkit. Everything below happens on the server, as root, in one interactive menu.

Before you start

  • A Linux server you control — Debian or Ubuntu, or Rocky/AlmaLinux 10+.
  • Root access, and a domain name whose A record points at it.
  • Port 80 and 443 reachable, at least long enough to get the first certificate.
  • Optional but recommended: a Grin node on the same box, from the same toolkit.

Get the toolkit

$ git clone https://github.com/noobvie/Grin-Node-Toolkit.git
$ cd Grin-Node-Toolkit
$ chmod +x grin-node-toolkit.sh
$ sudo ./grin-node-toolkit.sh

From the main menu choose Wallet & Payment Services, then Fidelius. The steps below are that screen, in order.

  1. Install the grin-wallet binaryDownloads the pinned official release and verifies its checksum.
  2. Install dependenciesNode.js, nginx, certbot, htpasswd, tor, qrencode and jq.
  3. Deploy files and the serviceInstalls the app and the systemd unit, listening on localhost only.
  4. Configure nginxWrites an HTTP-only virtual host first — a certificate cannot be referenced before it exists.
  5. Set up SSLLet’s Encrypt, or a Cloudflare origin certificate. This is where the site becomes HTTPS.
  6. Set up Basic AuthYour username and password. This is the entire authentication boundary — treat it that way.
  7. Configure the firewallOpens 80 and 443, and installs the fail2ban jail on failed logins.
  8. Status & infoShows what is installed, what is running, and the URL to open.
  9. Edit saved settingsChange the domain, the contact email or the auth user later, without reinstalling.
Order matters at steps 4 and 5. nginx refuses to start if a virtual host references a certificate file that is not there yet, so the HTTP host is written first and the certificate is fetched second. Running them out of order is the most common way to end up with a web server that will not come back up.

Optional: take it off the public internet

Menu key V holds the private-access path. Run it after the wallet already works publicly — it is a change of door, not a different install.

  1. Install WireGuardCreates the interface and opens the UDP port.
  2. Add a devicePrints a QR code to scan with the WireGuard app on your phone.
  3. DevicesList, revoke, or re-show a QR code.
  4. Certificate via DNS-01Re-issues the certificate so renewal proves domain control by TXT record, with no port needed.
  5. Switch to VPN-onlyRebinds nginx to the tunnel address. Refuses to run without a proven handshake.
  6. Revert to public HTTPSPuts it back, in one step.
  7. Diagnose accessChecks the tunnel, the binding, the certificate and the DNS answer, and names what is wrong.
If you use Cloudflare, the record pointing at your tunnel address must be DNS only — the grey cloud. A proxied record sends browsers to Cloudflare’s edge, which has no route to a private address.
