Wallet & payment services

The wallet hub — what a Grin wallet is, the fixed-slot menu, every wallet and payment product with its status, and the CMD wallet quick setup step by step.

Covers the toolkit as of 6 Nov 2026Page updated 6 Nov 2026Toolkit on GitHub

Main-menu option 5 opens the wallet hub: one screen that shows which wallet and payment products are installed and running on the server, and launches the one you pick. Each product is its own script with its own wallet, ports, nginx site and service. The hub itself installs nothing — except the CMD Wallet quick setup, which is built into it and is the fastest way to get a working command-line wallet next to your node.

Warning

Status — the main menu marks this hub (DEV). Two of its products are marked ✅ ready (the CMD wallet and Grin Drop), though the CMD wallet's screens have been rewritten since and have not yet run on a server (see the note in its section); the rest are marked building on the hub screen, and one — Accio — has never run on a server at all (see Accio below). Rehearse anything wallet-related on testnet first: the toolkit runs both networks side by side precisely so you can.

A Grin wallet, in plain words#

The node (from Script 01) keeps a copy of the chain and talks to other nodes. It holds no coins and no keys. A wallet is a separate program — grin-wallet — that holds a secret seed, derives keys from it, asks a node what is on the chain, and builds transactions. On this toolkit the wallet always talks to a node over the node's Foreign API (port 3413, testnet 13413); it can be your own node on the same server or a public node such as those Script 04 publishes.

Three things about Grin surprise people coming from Bitcoin:

  • There are no addresses on the chain. Nothing you receive is "sent to an address" that anyone can look up. A Grin wallet does have an address — a Slatepack address, grin1… on mainnet and tgrin1… on testnet — but it is a key for talking to the wallet, not a destination on the ledger.
  • Every transaction is a two-way exchange. The sender's wallet produces a partial transaction (a slate), the receiver's wallet signs it and hands it back, and the sender finalises and broadcasts it. Both wallets take part. That exchange can happen automatically when both are online, or by hand: the slate travels as a block of text called a slatepack that you copy and paste — in a chat, an email, on paper.
  • Coins that are sent to you need your wallet to answer. A wallet that is listening — running with its Foreign API open, ideally reachable over Tor at its slatepack address — receives without you doing anything. A wallet that is switched off receives nothing until the sender reaches it another way.

The toolkit's wallets move slates three ways: Tor (both wallets online; the sender connects to the receiver's address over the Tor network), slatepack text (copy and paste, either side may be offline), and — for products that support it — the Transporter, a store-and-forward queue from the Connectivity Hub (main menu 9) so the receiver can be offline at send time.

Two more terms you will meet on every wallet screen. The seed phrase — 24 words printed once when the wallet is created — is the wallet; anyone holding it holds the coins, and it is the only way to recover them on another machine. The passphrase encrypts the seed file on disk and is asked for every time the wallet is unlocked. The wallet exposes two local APIs of its own: the Foreign API (port 3415 / 13415) through which it receives, and the Owner API (3420 / 13420) through which it is managed; both stay on localhost and are never opened to the internet.

What the hub does#

  1. Probes each product — a config file, app folder or unit file for installed; a systemd unit, a tmux session or, for Grin XP, an nginx site link for running — and prints a status line for every one it finds. A fresh server shows No wallet services installed yet. WooCommerce never appears in that list, even when installed and running: the hub looks for grin-wallet-bridge-<net> units, while Script 053 creates grin-woo-bridge-<net> — check it from 053's own menu instead.
  2. Shows the menu below. Every key is live: a product key launches that product's script; a planned or spare key prints one screen explaining what the slot is for and returns, having installed nothing.
  3. Runs the CMD Wallet quick setup itself when you press A.

The hub prints a tip worth taking seriously: install each service on its own server. Every wallet product wants the wallet ports 3415 and 3420 (13415 / 13420 on testnet); two of them on one box collide, and a wallet holding real funds next to a public web service is a security mix you do not need. One server can still run the mainnet and testnet copies of a product together.

The menu#

This hub is the one place in the toolkit where menu keys are fixed slots and can be quoted safely: each category owns a block of keys ending in a spare, and a row keeps its key permanently — a new wallet takes slot 4, a new payment rail slot 8, and nothing below moves.

The CMD Wallet quick setup#

The CMD wallet is the plain grin-wallet binary, set up in /opt/grin/cmdwallet/<network>/ and left running as a listener in a tmux session so it can receive. There is no web page; you use it from the shell. It is the right first wallet to make: it exercises the same node link every other product depends on, and its screen tells you in plain terms whether that link works.

There is one wallet per network. You pick the network first, and that network's screen holds every action, so nothing further asks which network you mean.

Note

This whole flow — the network screens, Add, Renew, Configure, Fix network, Wipe and the listener screen — is read from the code. None of it has been run on a server yet. Rehearse it on testnet before you touch a mainnet wallet.

The two listener modes#

Every network's wallet runs in one of two modes, chosen during setup and remembered in .listen_mode:

ModePortWhat it can doTor
listen (default) — grin-wallet listenForeign API on 3415 / 13415Receive only. Other wallets can pay you; nothing can drive a send through this processgrin-wallet starts its own Tor for the listener, so the wallet is reachable at its grin1… address over Tor with nothing else to configure
owner_api — grin-wallet owner_apiOwner + Foreign API together on 3420 / 13420Receive and send, driven over HTTP. Required by anything that operates the wallet programmatically — the Transporter agent from the Connectivity Hub (main menu 9) cannot send through listen at allNo automatic Tor listener in this mode

Pick listen unless something needs to send through the wallet for you. You can switch later with 2) Configure, which leaves the wallet itself alone.

Note

Which Tor listen uses depends on the wallet's grin-wallet.toml. A wallet created by v5.5.0 gets use_integrated = true under [tor], so grin-wallet runs a Tor client built into itself (Arti); a toml written by an older release has no such key and keeps launching the system tor binary, which must then be installed. Either way the onion address comes from the wallet seed. This is read from the toolkit's notes on the upstream release, not observed on a server.

Setup, step by step#

Add, Renew and Configure are one flow, so the config steps can never differ between them. The banner names the action (CMD Wallet — Add wallet · MAINNET) and the script shows the target — network, node port, current listener mode, the wallet directory, the binary, the passphrase and seed file paths, the tmux session name — then runs the steps below. Configure skips step 2, and step 4 only follows a new wallet. Every toolkit prompt in these steps accepts 0 to cancel or skip; grin-wallet's own recovery prompts in step 2 do not.

The screen waits for Enter, so a printed seed phrase stays visible: write it down, then run 2) Configure to finish.

Replacing a wallet#

Renew asks all its questions before it touches the old wallet. In order:

  1. Replace it? (the new wallet takes over this network) [y/N/0 cancel]. Anything but y prints Nothing was changed.
  2. 1) New wallet or 2) Recover from seed, then the new passphrase, or Is your recovery phrase ready?
  3. A warning if a Transporter agent is wired to this wallet. On mainnet, Type MAINNET to confirm (0 cancel):, in exact capitals.
  4. The old wallet is retired. Its listener and every grin-wallet working in the folder are stopped. A mainnet wallet is moved to /opt/grin/cmdwallet/.retired/mainnet-<date_time>/; a testnet wallet is deleted. The binary, its version record and .listen_mode stay in place.
  5. grin-wallet init -h or init -hr runs.

A 0 before step 4 leaves the wallet as it was.

Danger

Step 4 happens before the new wallet exists, and nothing puts the old one back for you. If init then fails, or grin-wallet rejects your recovery phrase, the network has no working wallet: a testnet wallet's files are gone and only its seed phrase can rebuild it, and a mainnet wallet exists only in .retired/. Cancelling at a later prompt does not bring it back either. Before you Renew anything that ever held funds, make sure you hold the old wallet's seed phrase, and have the recovery phrase in front of you if you chose to recover.

Danger

To go back on mainnet after a failed Renew, use the folder Renew printed as Old wallet moved →, the one with wallet_data/ inside. If the network reads half-initialized, first run 5) Wipe (keep the binary) to clear the leftovers. Wipe moves them to a second, newer folder in .retired/, and the Restore: and Purge: lines it prints name that new folder, which holds no wallet. Do not restore from it. Stop the listener if one is running, move the contents of the older folder back into /opt/grin/cmdwallet/mainnet/, hidden files included, then run 2) Configure. That registers the wallet for backup again and asks for the listener mode, which Wipe reset to listen.

Add on a half-initialized network clears the leftovers first. A folder with a grin-wallet.toml but no wallet_data/wallet.seed holds no seed, so the script says Half-initialized wallet and clears it with no Replace it? and no MAINNET question (on mainnet it is moved to .retired/ too, on testnet deleted). A folder with a seed but no toml is different: Add then asks both of those questions, exactly as Renew does, because a seed is there.

After it finishes#

tmux ls                                        # grin_mainnet_cmd_wallet
tmux attach -t grin_mainnet_cmd_wallet         # the listener's output; Ctrl+B then D to detach

A healthy listen-mode session shows grin-wallet starting the Foreign listener on 127.0.0.1:3415 and, a little later, a Tor .onion (the wallet's slatepack address in onion form). Balance and history come from the wallet's own commands, run from the wallet directory (add --testnet for the testnet wallet); each asks for the passphrase:

cd /opt/grin/cmdwallet/mainnet
./grin-wallet info        # balance: total, awaiting confirmation, currently spendable
./grin-wallet address     # your grin1… slatepack address — give this to people paying you
./grin-wallet txs         # transaction history

To pay someone, ./grin-wallet send -d <address> <amount> (their grin1… address) tries to reach them over Tor and, if it cannot, prints a slatepack for you to pass on by hand; they run receive, send the reply back, and you finalize it. The full command-line flow is in the Grin wallet documentation.

Note

The script's own comments say a running listener holds the wallet database lock, so a second grin-wallet command in the same directory may block until it times out. If info hangs, stop the listener first (1) Listener → 2) Stop), run the command, then start it again (1) Start). This was taken from the code, not observed on a server.

Fix network (F)#

grin-wallet takes its chain from chain_type in the toml whenever a toml exists; --testnet only decides what a new toml gets. So a testnet toml sitting in the mainnet folder runs as testnet, with ports that make it look like mainnet, and hands out an address nobody on mainnet can pay. The toolkit reads the toml (no passphrase needed) and flags three things: a chain_type that does not match the folder's network, a local node address on the wrong port, and wallet data kept outside the wallet folder. A remote node address is not checked, because its port says nothing about its network.

When one of these is true, the overview row says ▲ wrong network, and the network's screen shows ▲ This wallet is on the wrong network, each problem, and F) Fix network correct the toml — seed and keys unchanged. Until it is fixed, 2) Configure, Start and Restart all refuse. Stop, Renew, Wipe and B still work.

F lists what it will change, warns if a Transporter agent is wired to this wallet, and asks Fix the <network> wallet? [y/N/0 cancel]. On y it:

  1. Stops this wallet's listener.
  2. Keeps a copy of the toml as grin-wallet.toml.before-network-fix-<date_time>.
  3. Sets chain_type, both listen ports, the local node address and the live node's secret, on a copy that replaces the toml only if every edit took. A remote node is left as it is and gets no local secret.

The seed and keys do not change. The address keeps its key and takes the right network's prefix. The listener is left stopped on purpose, because what the wallet recorded on the other chain stays until you clear it. Run this first (it asks for the passphrase), then start it from 1) Listener:

cd /opt/grin/cmdwallet/<network> && ./grin-wallet scan -d

If the wallet data is outside the folder, F refuses with Not repaired: this toml runs on the wallet data in <dir>., because correcting the network here would not change which wallet is in use. Set data_file_dir in the toml by hand, or Renew to start clean; Renew does not touch data kept outside the wallet folder.

Wipe: start a network over#

5) Wipe removes this network's CMD wallet and leaves the network empty — useful when testing. It shows what it found (whether a seed exists, whether the listener runs, whether a saved seed copy is on the box; on mainnet with no saved copy it reminds you to hold the phrase), and collects every answer before it touches anything:

  1. Keep the grin-wallet binary, so Add skips the download? [Y/n/0 cancel], asked only when a binary is there. Y keeps the binary and its version record; n takes the whole folder.
  2. Wipe the <network> CMD wallet? [y/N/0 cancel], and on mainnet also Type MAINNET to confirm (0 cancel):.

It then stops the listener and every grin-wallet working in that folder, removes everything else in the folder — the toml, wallet_data/, tor/, the saved passphrase and seed files, the logs, listen.sh and .listen_mode, so the next Add starts from mode listen — and deletes the wallet's line from /opt/grin/conf/grin_wallets_location.conf so the toolkit backup stops collecting an empty folder (Add puts it back). A testnet wallet is deleted. A mainnet wallet is moved to /opt/grin/cmdwallet/.retired/mainnet-<date_time>/, and the screen prints how to put it back (stop the listener, move the contents back into /opt/grin/cmdwallet/mainnet/, hidden files included; if you answered n above, create that folder first) and how to purge it (rm -rf that folder, once you are sure it holds nothing). After a move back, 2) Configure registers the wallet for backup again. If a Transporter agent from the Connectivity Hub is wired to this wallet, the screen warns that the agent's settings are not changed — re-run the agent's wallet step afterwards. Renew gives the same warning and makes the same mainnet move.

Accio — the public web wallet (not yet run)#

Warning

Status — Accio is written but has never run on any server. No build, no deployment, no send and no receive has ever been performed on a VPS. Hub key 2 opens its menu and every option there is real code, but none of it has been exercised end to end. Do not put funds through it, and do not offer it to anyone until an acceptance run on testnet has been done. There is no manual page for it until then.

What it is meant to become: a wallet that anyone can open in a browser at your domain, where the seed is generated and kept in the visitor's browser tab — the exact opposite of Fidelius, where the server holds the keys. The browser code is a vendored, integrity-checked copy of an MIT-licensed upstream wallet that already supports Grin; the toolkit adds a small Node.js gateway (ports 7480 mainnet / 7490 testnet) that forwards the visitor's Tor sends and relays incoming payments to the open tab, an nginx site with HTTPS, an optional .onion front, and an offline standalone HTML file that can send but not receive. Its menu today, per network: install/deploy, rebuild the site, gateway service, nginx/SSL/onion, check upstream, build the standalone file, status, uninstall — under a banner that says NOT YET PROVEN ON A LIVE BOX. The design and build log are in the toolkit's script052_design.md and script052_implementation.md.
