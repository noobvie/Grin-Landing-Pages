Run a public mining pool

How Script 07 deploys GRINIUM, a self-hosted PPLNS Grin pool with no miner accounts, Tor and slatepack payouts, an admin panel and optional regional gateways.

Covers the toolkit as of 6 Nov 2026Page updated 6 Nov 2026Toolkit on GitHub

The public pool is the second half of the mining hub (the first half, solo mining, has its own page). It turns your node into a mining pool that other people point their rigs at: a stratum server on a public port, a website with live stats, a per-miner account page, and an admin panel where you set the fee and watch the money. The toolkit's job is the infrastructure — Node.js app, database, systemd, nginx and SSL, the pool wallet, backups. Every business decision (name, fee, payout floor) is made in the web admin panel after setup, not in a config file.

You need a synced mainnet node from Script 01 (pruned is fine), a domain, and a passphrase for the pool wallet the setup creates.

Warning

Status — the main menu does not mark the mining hub (DEV), but this product is still being built. The reference pool, grinium.com, runs on mainnet with real miners, and that is where the toolkit's pool is tested. Its first Tor payout, in September 2026, failed because the pool could not find grin-wallet (fixed since). Much of what is on this page was built after that and has not run on a server yet: Tor payouts as they work now (one attempt per payout), the stratum pause, the hub move (Migrate OUT / IN), operator revenue withdrawals, the /play/ games service, the gateway latency probe, the Goblin rail, the daily giveaway, the fee rate recorded on each block, and late and lost block reporting. Make your first payouts small, and read Fees and payouts before you announce a fee. Nothing on this page should be read as "proven in production".

What you get#

For a miner, the pool works like the large Grin pools: there is no sign-up. The rig logs in to pool.yourdomain.com:3333 with its Grin slatepack address as the username (optionally address.rigname), and that address is the account. A public account page shows its hashrate, workers, share quality, balance and payout history; the pool pays to that same address, so a miner can be paid without ever having had a login. There is no login to steal.

For you, the operator:

  • a stratum proxy in front of the node's built-in stratum that counts every share, on your own public port;
  • PPLNS reward sharing, block maturity tracking, orphan detection with exact reversal;
  • payouts to miners over Tor (the pool's wallet talks straight to the miner's wallet) or by slatepack (copy-paste), plus a Goblin rail that is off by default;
  • a stratum pause: close every stratum port for a set time from the admin panel, with a notice on the public site;
  • a website (dashboard, blocks, miners, payments, network map, blog, pages) with a white-label branding system and 14 themes (two enabled out of the box);
  • an admin panel with a full money statement, a payout kill-switch, operator revenue withdrawals, sessions, regions, ads, incentives, CMS;
  • regional gateways: thin stratum forwarders on other continents that tunnel miners to this box, added later without a rebuild;
  • an encrypted backup, a guided move to a new server, and a JSON API documented at /api-docs.html on your domain;
  • optionally, Play & chat: a /play/ games and chat service for your miners, run as its own process beside the pool.

The deep design — why address-as-identity, why SQLite, why Tor — is in the toolkit's script07_design.md; this page is the operator's manual.

What it does#

The pool server install (the Pool server mode) puts these on the box:

  1. Node.js 24 from NodeSource (the pool uses Node's built-in SQLite, so 24 is a hard minimum), logrotate, sqlite3, wireguard-tools (only used if you add gateways later) and fail2ban. The pool app is copied to /opt/grin/pubpool/mainnet/, its dependencies installed with npm ci.
  2. A systemd service grin-pool-manager running as the unprivileged grinpool user under a hardened unit, plus a fail2ban jail on the admin login and the grin-gateway-ctl helper the multi-region path uses. The service logs to the systemd journal: read it with journalctl -u grin-pool-manager. The install also adds a logrotate rule for /opt/grin/logs/grin-pool.log, but that file is not the service log.
  3. A config file /opt/grin/conf/grin_pubpool.json seeded with defaults (fee 1 %, payout floor 25 GRIN, ports) and a random JWT secret.
  4. The website in /var/www/grin-pool/ with the admin panel under /admin/.
  5. An nginx vhost for your domain — HTTP first, then a Let's Encrypt certificate, then the full HTTPS vhost with rate-limit zones, security-header snippets, Cloudflare real-IP support if you want it, and an optional IP allowlist on /admin/. If nginx or certbot is missing, this step offers to install them.
  6. A pool wallet in /opt/grin/pubpoolwallet/mainnet/: its own grin-wallet binary, a new or recovered seed, and one combined listener on port 3420 that serves both wallet APIs — the node's stratum calls it to build the coinbase of every block template, and the pool backend calls it to send payouts. The passphrase is saved to a mode-600 file owned by the service user and the listener is unlocked over the encrypted Owner API; it is never on a long-running command line. This step also installs the toolkit's grin-secret-sync timer.
  7. The first admin account, created from the box over loopback; the public registration route closes as soon as one admin exists.

One thing the menu does not do for you: the node's own stratum server has to be switched on and the node restarted. See Wire the node and restart it — skip it and the pool has no work to hand out.

Choices you will make#

Mainnet or testnet#

Pick the network on the mining hub's menu, before the pool script even starts. Mainnet is the real pool, with real GRIN. The hub also offers a testnet pool: a fully independent install — grin-pool-manager-testnet, /opt/grin/pubpool/testnet/, config grin_pubpool_testnet.json, API port 8090, stratum 13333, wallet port 13420, a tgrin1… address, block maturity 100 instead of 1440 — that needs its own domain and a testnet node, and can share a box with a mainnet pool. The toolkit's own pool is tested on mainnet only, so nothing on this page has been checked against the testnet mode.

One server, or a pool server plus regional gateways#

A single Pool server serves every miner in the world on its own port 3333 as region main. That is the normal pool and the only thing you need. If you later want lower latency for miners on another continent, you add a regional gateway — a separate small VPS that runs a stratum forwarder and a WireGuard tunnel back to the pool server, and nothing else — without rebuilding anything. See Regional gateways. An advanced third mode, Central Hub (a brain with no local stratum, all mining arriving through gateways), is not on the menu; it is started with bash 07_grin_mining_public_pool.sh hub.

Behind Cloudflare?#

Setup nginx asks once, default yes. Most public pools front their site with Cloudflare's proxy, and behind it every visitor arrives from a Cloudflare IP — so the toolkit restores the real visitor address from CF-Connecting-IP, otherwise the rate limiter and fail2ban would treat all visitors as one. Answer n if your DNS points straight at the box. If you are behind Cloudflare, the script also prints a ufw recipe to allow 80/443 only from Cloudflare's ranges, so nobody can talk to the origin directly.

Who may open the admin panel#

By default the admin panel is reachable from any IP — the login form, captcha, per-account lockout, IP auto-ban, optional two-factor and fail2ban are the only gate. The script tells you so twice. Once the pool is live, put your own IP (or VPN range) into admin_allowlist in the pool config and re-run Setup nginx: /admin/ and /api/admin/ then answer 403 to everyone else, with localhost always allowed as the break-glass path. Once the list holds at least one entry, the summary at the end of the guided setup prints a one-line node -e … command that adds a further IP for you; the first entry you type into the config yourself (S on the pool menu).

Wire the node and restart it#

Script 01 deliberately leaves the node's built-in stratum server switched off — mining is Script 07's business. The pool relies on the toolkit's grin-secret-sync timer (step 5 installs it) to flip it on: every 5 minutes it checks grin-server.toml and sets enable_stratum_server = true, stratum_server_addr = "127.0.0.1:3416" and the wallet_listener_url that step 5 also patched. It only rewrites keys already in the file, which a toolkit-built node has. Those keys are read only at node start-up, so the node must be restarted once after the wallet setup. Do it right away rather than waiting for the timer:

grin-secret-sync                        # applies the stratum keys now; says RESTART if it changed them

Then restart the node from Script 01 → Stop a node, followed by Start a node (or, if the sync watchdog is installed, stop it and let the watchdog bring it back within 5 minutes). Confirm the node's stratum is listening before you announce the pool:

ss -tlnp | grep 3416                    # the node's stratum, localhost only
cd /opt/grin/node/mainnet-prune
grep -E 'enable_stratum|stratum_server_addr|wallet_listener_url' grin-server.toml
Note

The guided setup prints "complete" before this step, and nothing in the menu says the node needs restarting except the wallet step's one-line warning. Until you do it, the service journal shows the pool failing to log in to the node stratum and every miner sees no jobs. This is a gap in the script, not in your setup.

The same timer puts the three keys back after a Script 01 rebuild regenerates grin-server.toml, and prints RESTART the mainnet node when it did; restart the node again after any rebuild.

After it finishes#

Two more things the setup leaves to you, both in the wallet submenu (5): enable Auto-restart on boot (6 → e) and install the watchdog (7 → i). After a reboot the wallet's decrypted seed is gone from memory; without these, the listener stays down or locked and the pool issues no work until you log in and fix it by hand. The watchdog runs every 5 minutes and relaunches or re-unlocks the listener.

Now check the parts:

systemctl status grin-pool-manager --no-pager      # active (running), User=grinpool
ss -tlnp | grep -E ':(3333|8080|3420|3416) '       # stratum, API, wallet, node stratum
journalctl -u grin-pool-manager -n 30 --no-pager   # look for "Login accepted by node stratum"
tmux attach -t grin_pubpoolwallet                   # the wallet listener; Ctrl+B D to leave
curl -s https://pool.yourdomain.com/api/pool/poolstats | python3 -m json.tool

On a testnet pool the service is grin-pool-manager-testnet: use that name with systemctl and journalctl. The last command is the public stats feed; a JSON document with your pool name, hashrate and block count proves nginx, the API and the database are all talking. Open https://pool.yourdomain.com and its /login.html; sign in with the admin account you created.

Then point a rig at it. Any Grin miner that speaks stratum works (iPollo G1 and G1-Mini, lolMiner, GMiner…); the connect card on the homepage shows the exact endpoint and a mock of a miner's Pool Setting form:

Pool URL   pool.yourdomain.com:3333        (bare host:port; no stratum+tcp:// prefix needed)
Worker     grin1…your 62-character slatepack address….rig1
Password   anything but a trivial one — see below

A bare worker name without the address is rejected: the address is the identity. The password is not an account password — the pool keeps a hash of it, and of the rig's IP, from the rig's first accepted shares (up to ten of each per address), and they later serve as proof of ownership when that address requests a payout. Trivial passwords (x, 123, the miner defaults) are ignored for that purpose, so tell your miners to set a real one.

The admin panel#

Sign in at https://<domain>/login.html; it redirects to /admin/. There are no default credentials: the only admin is the one step 7 created on the box, and registration closed the moment it existed. The session is an httpOnly cookie with an idle timeout and a hard maximum lifetime, both set under Access Control. Money-moving and destructive actions ask for your password again in an in-page dialog (step-up), and you can require two-factor for every admin. Every admin page has a search box that finds a page, a section or a single setting.

The left rail has four groups:

Changing the fee, the payout floor or the retention windows takes effect on save (a few keys say applied at restart on the page). A fee save reaches the public pages at once and applies to every block found from then on, so announce a change to your miners before you save it.

The payout freeze is a kill-switch on the Payouts pages (Queue and Treasury). Engaged, the pool stops every outbound send — Tor, slatepack, Goblin — while still refunding expired slates to miners. The alert monitor engages it on its own when the money checks trip (wallet balance below what miners are owed, ledger totals that no longer agree, a balance that moved without a ledger row, a different wallet answering); a restore engages it too; you engage it by hand when a wallet or box looks compromised, or before you swap the wallet. Miners see a payouts paused chip on their account page, never the reason. Resume from the same place once you understand what happened.

Locked out? A) Admin recovery on the pool menu needs a root shell on the box and nothing else: list the admin accounts, clear a lost authenticator, set a new password (prompted, never on the command line), mint new recovery codes, or clear a failed-login lockout. Every action writes an audit row.

Fees and payouts#

The pool fee is a percentage of each block reward, taken when the block matures — 1440 confirmations on mainnet (about a day) — never at withdrawal time; 0 % is allowed, for a promotion (the flat withdrawal fee below still applies). The rate is the one in force when the share that solved the block reached the pool. It is recorded on the block, so a fee change while that block matures does not touch it. The public Blocks page shows each block's rate in a Fee column (— for an orphan or a rate not on record), the Payments page tile Current pool fee shows the live rate, and the admin fee-revenue.csv export uses each block's own rate. On a pool upgraded from before the rate was recorded, settled blocks get their rate back from the ledger or stay "not on record", and blocks still maturing at the first start take the rate the pool booted with. Rewards are shared PPLNS over the shares submitted in the last 60 blocks, so a miner who leaves just before a block is found still gets their share of it, and pool hopping does not pay. A block that turns out to be an orphan has its exact credits reversed from every account it paid, fee included. Balances are the miner's to withdraw once they reach the minimum withdrawal, 25 GRIN by default (each payout is an interactive transaction that leaves a permanent kernel on chain, hence the high floor). A flat withdrawal fee, 0.04 GRIN by default and never less, is deducted from each payout to cover the network fee the pool pays as sender.

Payouts are requested by the miner, not sent on a schedule — there is no automatic payout. On their account page the miner proves they own the address — by giving the IP one of their rigs has mined from, or a rig's stratum password — enters an amount, and picks a rail:

RailHow it works
Tor (the default)The pool wallet sends straight to the miner's wallet over Tor, the miner's wallet signs automatically, the pool finalises and broadcasts. A pre-flight check refuses the request at once if the miner's wallet does not answer over Tor. The send is tried once and ends Paid, Failed (balance returned at once, and the page offers Slatepack instead) or Held (see below). It is never re-sent. The miner needs a wallet with its Tor listener running at the moment of payout (Grim, grin-wallet listen, Fidelius…)
SlatepackThe pool prepares the transaction and shows it as a slatepack, encrypted to the miner's address so nobody else can read it; the miner pastes it into their wallet, pastes the response back, the pool finalises. The miner needs any wallet that can receive a slatepack, and has 30 minutes by default (the Slatepack Response Window) to answer before the funds go back to their balance
GoblinDelivery as a Nostr direct message to a registered Goblin name — this pays a third party, so it is off unless you switch it on, and comes with a domain allowlist, a 48-hour cooldown on a newly registered name, and registration needs both proofs (IP and password), each at least an hour old. The miner needs a Goblin wallet

Only one payout per address can be in flight, and after a reversed payout (an expired slatepack, a failed Goblin send, an admin cancel) the address waits 30 minutes before trying again; a failed Tor payout does not start that wait. After five failed Tor payouts in 24 hours, Tor is paused for that address for 24 hours. The account page also lets a miner fetch a signed payment proof for every confirmed payout.

Held payouts. When the pool genuinely cannot tell whether a Tor send went out (it timed out, say), the amount stays locked and the row is Held. The pool reads its wallet's transaction log every pass and settles the row by itself: confirmed on chain → Paid; absent on two reads at least 10 minutes apart → refunded. Both reads must be taken while payouts are unfrozen, so after a restore or a Migrate IN a held row waits until you unfreeze. A payout held for more than 24 hours raises a critical alert. The Queue page has Re-check and, after a password and typing the payout id back, Forced refund; neither ever sends money.

What you, the operator, do with the money: the fee accrues in an internal pool_fee account and stays in the pool wallet. Withdraw it from Payouts → Queue → Operator revenue → your wallet: save a revenue address once (a change to it waits 24 hours and raises an alert), then withdraw; these withdrawals are listed publicly on the Payments page. Do not move the fee with a raw grin-wallet send: the ledger would not know, the wallet would no longer cover what it owes, and the reconciliation would freeze payouts. Keep the hot balance low — the pool wallet is unlocked 24/7 by design (it must be, to sign coinbases), so treat it as a cash register, not a vault.

The daily giveaway#

An optional daily prize, set under Settings → Incentives → Daily Giveaway. It is off by default and needs two switches: Run the daily giveaway and Enable incentive features (master switch). The lottery switch is not needed. Saving asks for your password again.

FieldDefaultLimits
Minimum per day, Maximum per day (GRIN)1, 5Each at least 0.000000001 and below 60 GRIN (one block reward), refused on save otherwise. Keep them far below it: a day's total worth more than a block could make it pay a miner to throw a block away for a different result
Minimum prizes per day, Maximum prizes per day1, 31–1000
Hours mined that day to qualify61–24

In each pair the minimum must not exceed the maximum.

Who enters. Any address with at least that many hours of mining inside the UTC day, counted from its hashrate records with a non-zero rate. Only minutes with an accepted share count, so a very slow rig may need longer than the setting. Banned addresses and the internal pool_fee and prize_pool accounts never enter.

How a draw is decided. Everything comes from the hash of a seed block chosen in advance. The pool rolls one total between your two amounts and one prize count between your two counts. The total is capped at the prize pool as it stood when the draw opened. Prizes are equal: each is rounded down to the nanogrin, and the dust stays in the prize pool. Each prize is then its own pick from the whole entry list, weighted by that day's work. There is no cap and no one-win limit: one miner can win several prizes in a day, and a big miner wins often, in proportion to their work. Splitting across addresses gains nothing. Fewer miners than prizes means more wins each, not a smaller total. The seed block is public but the entry list is not, so nobody outside the pool can recompute a draw; do not tell your miners they can.

When it runs. The job runs once an hour, counted from when the service started, with no run at start itself. The first run after 00:00 UTC opens the draw for the last completed UTC day and names a seed block 10 blocks ahead, and the next run pays. That is the "within about two hours of 00:00 UTC" on the page, but repeated restarts inside an hour push it back. If you switch the giveaway on during the day, the next run opens a draw for yesterday. Only the last completed day is ever drawn: a pool that was down for three days does not pay three days. A day with no qualifying miner closes with nothing paid.

Where the money goes. Prizes come from the prize pool only, in one debit per draw, and a draw pays all its winners or none. A prize lands on the miner's pool balance (ledger label prize won), so it can be withdrawn once the balance reaches the minimum withdrawal. Prizes count in the Given away tile on the Payments page.

When a draw waits or is lost:

  • Prize pool below your minimum, or the node not answering, when the draw would open: no draw, retried every hour. A top-up before the end of the UTC day after the one being drawn still draws it; otherwise that day is skipped for good.
  • Giveaway switched off after the draw opened: On hold until you switch it back on. Switching off never closes an open draw.
  • Prize pool cannot cover the draw when it pays: On hold until you top it up.
  • A winner banned before the draw pays: loses that share, and it stays in the prize pool. If every winner is banned, the draw closes with nothing paid.

On the page: Preview 7 days moves no money; it simulates a week on the saved limits, shows the real odds above the simulated days, and Pretend extra miners (capacity test) (0–1000) tests load, not odds. Run a real draw now spends prize pool GRIN: an extra draw over the last 24 hours that does not replace the scheduled one, pays once its seed block exists, and needs a browser confirmation and your password; only one can be open at a time. Recent giveaway draws lists each draw and its state, with Refresh.

What miners see: while the giveaway is on, a Daily giveaway panel on /fortune-board.html. The pot filter and chart on that page list the giveaway too. The account page shows Draw prizes won: N (X GRIN in total), which counts every draw the address has won, not only this one.

Late and lost blocks#

The pool waits 15 seconds for the node to answer a submit, then tells the miner the share failed. A frozen node can still have taken that submit as a block, so the pool keeps checking:

  • The node's reply arrives within 10 minutes of the timeout: the block is recorded as usual, at the fee in force when the submit arrived.
  • No reply comes (the link dropped, or 10 minutes passed): the pool reads the chain, one header per height, retrying for about an hour. A match is reported, not credited: a nonce and proof are public once a block is out, so a miner on a stalled job could have sent a stranger's block. The alert tells you to confirm first that the pool wallet holds that block's coinbase.
  • The node accepted a block but the share row could not be stored: the block is still recorded.

This check lives in memory, so a pool restart forgets what it was still holding.

Warning

These alerts say a block must be "entered by hand", but neither the pool menu nor the admin panel can do that, and this manual has no procedure for it. Until the block is entered, its reward stays in the wallet and is not shared out. Keep the alert text: it carries the height, hash and, when it can tell, the finder.

Note

The block and share alerts here, and Daily Giveaway Stopped, do not appear on System Health or anywhere else in the admin panel. They go to the service journal (journalctl -u grin-pool-manager), where Shares Not Recorded and Daily Giveaway Stopped appear only by internal name (Alert triggered: share_record_failed, giveaway_rules_invalid), and to any alert channel you set in the pool config with S, then a service restart: discord_webhook_url, slack_webhook_url, telegram_bot_token with telegram_chat_id, or alert_email_address with an smtp block that sets enabled to true. A pool with no channel set tells you nothing unless you read the journal. All of this is read from code, not seen working.

The pool wallet#

5 on the pool menu opens the wallet submenu:

  1) Set up wallet        (install + init/recover + save pass/address + start)
  2) Start listener       (owner_api + include_foreign, Owner+Foreign 3420, auto-unlock)
  3) Stop listener
  4) Show pool address
  5) Patch node wallet_listener_url
  6) Auto-restart on boot (enable / disable)
  7) Watchdog */5        (install / remove)
  8) Replace pool wallet  (compromise/corruption runbook — balances live in pool.db)
  9) grin-wallet binary   (update · roll back · verify — seed and pool.db untouched)
  0) Back

Two facts make the pool wallet different from a personal one. It runs one listener that serves both wallet APIs on port 3420: the node's stratum calls it to build the coinbase of every block template it sends to miners (a local signing operation — the seed must be decrypted in memory), and the pool backend calls it to check balances and send payouts. And a locked wallet stops the pool, not just the rewards: no coinbase, no block template, no jobs. That is why the passphrase lives on disk and why autostart and the watchdog matter.

The listener runs grin-wallet owner_api only and never publishes a Tor onion of its own. If the status line warns that a Tor hidden service or a grin-wallet listen points at the pool wallet, remove it: a miner's wallet could then finalise a payout behind the backend's back.

8 is the runbook for a compromised or corrupted wallet: because every miner's balance lives in pool.db and not in the wallet, you can swap in a fresh wallet without losing any accounting — freeze payouts first, sweep the old one if you still can, remember that coinbases younger than 1440 blocks cannot move yet, and re-run the node restart above. 9 updates or rolls back the grin-wallet binary from the toolkit's shared store; the seed and the database are untouched.

Pause the stratum#

Settings → Announcements → Stratum in the admin panel closes every stratum port — the public 3333 and every gateway's region port — so that during a restore, a move or database trouble no share is accepted that the pool cannot credit. Pausing waits up to 30 seconds for shares already in flight (a block found in that moment is still credited), then drops every miner. If a timed-out submit could still turn out to be a block, the result reads Paused · settled, but wait before a hub migration. The website, the API and payouts keep running.

  • Pause for 15, 30, 60 or 120 minutes, with a reason (admin-only, never published). Every pause ends on its own; Extend sets a new end time, and Resume ends it early.
  • Schedule a window for later: 5 minutes to 6 hours long, starting at least 15 minutes ahead and at most 30 days ahead. Times are entered in UTC.
  • While paused, the public site shows a maintenance notice with the expected time back ("Mining is paused until about 05 Oct 14:30 UTC"), and a banner announces a scheduled window from 24 hours before it. The notice text is set in the Maintenance Mode card on the same page.
  • A red strip on every admin page says the stratum is paused, or degraded if a port failed to open again on resume (the strip names the port and offers Re-bind).

Every action asks for your password again. A pause survives a restart of the service: the pool comes back paused until the same time. A restore and a Migrate IN start the pool paused for up to 2 hours.

Regional gateways (multi-region)#

Optional, and the W menu says so in capitals: a normal pool never needs it. A regional gateway is a small VPS near a group of distant miners that runs exactly two things — HAProxy forwarding raw stratum TCP, and a WireGuard tunnel to your pool server. It has no Grin node, no wallet, no database, no Node.js, and holds no keys but its own tunnel key. Miners connect to its port 3333; their traffic arrives at the pool server on a private per-region port (3391, 3392… on the tunnel interface only) with the miner's real IP carried in a PROXY-protocol header, and the pool stamps those shares with the region so the connect page can show per-region status and latency.

The W menu on the pool server:

  1) Setup WireGuard server   (install, keys, tunnel, firewall, pairing helper)
  2) Add a gateway peer       (assign tunnel IP + region port)
  3) List gateways / regions
  4) Remove a gateway        (revoke wg key, free port mapping, drop admin card)
  5) Hub endpoint DNS name   (survive a provider/IP change without re-pairing)

The gateway box's own menu (mining hub → public pool → 2) Regional gateway):

  1) Install            (haproxy + wireguard; generate keypair)
  2) Configure          (region, central endpoint, tunnel keys)
  3) Bring up tunnel    (wg-quick up wg-grinpool + hub re-resolve timer; re-run once to add it)
  4) Service control    (start / stop / restart forwarder)
  5) Status
  6) Latency probe      (HTTPS /ping so the pool's connect page can time this gateway)

Pairing is a two-box dance. The pool server assigns everything; the gateway only pastes. The admin panel's Regions page does the pool-server half too, and is the better path: it opens the new region's listener without restarting the pool, while W → 2 needs a service restart (it asks).

Replacing a gateway box: do not remove the old peer first. Install the new box, then add its public key under the same region key (W → 2, or the region's card in admin Regions): the pool swaps the key in place, keeps the region's tunnel IP and port, and hands back a pairing line for the new box. DNS and the region card do not change; only the A record moves if the new box has a new IP.

Removing a gateway (W → 4) asks you to type the region key twice, revokes its key, deletes its port mapping and its card in admin Regions, and then restarts the pool service straight away, without asking, which drops every miner on every region for a few seconds. The freed port is never reused: pairing that gateway again later gives it a new tunnel IP and port. W → 5 puts a DNS name instead of an IP into pairing strings, so a later change of the pool server's address is one DNS edit rather than a visit to every gateway. Update the toolkit on both boxes together: a pairing string from a newer pool server is rejected by an older gateway.

Latency probe (optional). The connect page can time each gateway from the visitor's browser. Gateway 6 → 1 asks for the gateway's public hostname — the same name miners use for that region — gets a certificate for it with certbot --standalone, and answers https://<host>/ping on port 443 with an empty reply and nothing else. It needs TCP 80 (at issue and at every renewal) and 443 open on the gateway. The stratum forwarder is a separate process and is not restarted. The pool's website may only time hosts under its own domain name: with the pool at pool.yourdomain.com it can time nyc.pool.yourdomain.com but not nyc.yourdomain.com. For the second kind, set latency_probe_domain in the pool config to the parent domain you own (yourdomain.com) and re-run pool menu 4; until then the browser blocks the probe and the connect page keeps its estimate.

Warning

A gateway is fully trusted. It reads every miner's login in clear (their address and rig password) and it asserts each miner's IP — the two things the pool accepts as proof of ownership at payout time. Run gateways only on servers you control as tightly as the pool server; do not let a partner operate one. The reasoning and alternatives are in the security audit's §J16-2.

One encrypted archive per network per day lands in /opt/grin/backups/, named grin_pubpool_backup_ plus the date and .tar.gz.enc, holding everything a fresh install cannot regenerate: a consistent snapshot of pool.db (taken with SQLite's online-backup API, never a raw copy of a live file), the pool config with its JWT secret and region map, the wallet directory (seed and config, not the binary), .wallet_pass, uploaded media, the WireGuard identity, the nginx vhost, and the games database when /play/ is installed. The TLS certificate is not in it. The archive password is your personal key followed by the date in the file name — the key is set in Settings and must be kept off the box, or the backup is worthless when you need it. The same engine and key scheme serve the toolkit's other products — see Back up and restore.

Restoring (2) asks you to type RESTORE (and, when /play/ is installed, separately whether to restore the games database, default yes), then stops the service and the wallet listener, extracts the archive over the original paths, freezes payouts on the restored ledger and pauses the stratum for 2 hours. On a fresh server the order is Script 01 node → pool 1) Install → B → 2, then those steps.

Move the pool to a new server#

B → 6 Migrate OUT and B → 7 Migrate IN move a live pool to a new box with every balance, share, hashrate history, audit row, the wallet seed, the WireGuard identity and the TLS certificate, and as little downtime as possible. Both refuse to start until you type MIGRATE.

  1. Days before, on the new box: build the node with Script 01, run only pool 1) Install (not 5) Set up wallet: it would mint a seed the restore replaces, and CHECK warns about it), then B → 7 and type CHECK. It is read-only: it checks the node is synced, nginx and certbot, the firewall, Tor, and prints a fingerprint of the backend code. The old box's Migrate OUT prints the same fingerprint, and the two must match (update whichever box is behind). If the pool takes a new region tag at its new home, create that region's DNS record now (DNS only, no proxy, TTL 60). Fix every ✗ while the old pool still serves.
  2. On the old box, optionally pause the stratum for 60 minutes and wait for "settled". If the panel says Paused · settled, but wait before a hub migration., keep the pool running for 15 minutes with the node healthy first: a restart forgets the lost submits it is still checking, and Migrate OUT does not check this for you. Then B → 6 Migrate OUT: freezes payouts first; stops the wallet listener and removes its watchdog and boot autostart; turns off the VACUUM cron; stops and disables the pool service, the games service and the WireGuard tunnel; turns off the daily backup; writes a manifest of the ledger figures; takes a final encrypted archive (with the certificate — the only archive that carries one) and verifies it; and copies it to the new box with scp, or prints the command. Miners disconnect now, and this box will not start the pool again, not even after a reboot. The node keeps running.
  3. On the new box, B → 7, type MIGRATE: checks again, and that the old pool is dark (it must not answer on its stratum port or its API); restores with payouts frozen; asks for a new region tag if the pool moved; brings up node secrets, wallet, web files, WireGuard and nginx; then compares every balance, count and highest id with the manifest — any ✗ stops here, before anything starts. Then it starts the wallet and the pool with the stratum paused (up to 2 hours) and prints the DNS records to change.
  4. Change DNS, resume the stratum on the new pool as soon as the continuity check is all ✓ (waiting for the automatic resume is pure downtime), watch the gateways come back, reconcile, and unfreeze payouts. Never start the old pool again.
Note

Migrate OUT and IN have not been run on a server yet. A failed step is safe to repeat: fix the cause and run the same menu item again. Nothing in either half ever unfreezes payouts.

Removing the pool#

Danger

Enter at the first question of Z cancels. After you answer y, Enter still removes most of the install: two groups default to no ([y/N]), the app directory with pool.db and .wallet_pass, and the games database, and every other group defaults to yes ([Y/n]). That includes the config file with jwt_secret, pool_address and the region map, and the WireGuard tunnels and their keys. On those groups answer exactly n: typing no removes the group anyway, except on the games service question. Take a backup (B → 1) first.

Z on the mode-selector menu previews what is present, asks for one master confirmation and then confirms each group: services and units, the games service and (separately) its database, the app directory with pool.db and .wallet_pass, gateway files and tunnels, web root, vhost, zones and snippets, cron and logrotate and the helpers, the JSON configs, logs, the fail2ban jail. It never touches the node, its chain data or grin-server.toml (the stratum keys stay as they are and the next install reuses them), the wallet directory and seed, or the backups in /opt/grin/backups/. Take a backup first if there is any balance in the database — the app directory group, if you answer y, deletes every miner's ledger. The TLS certificate stays in /etc/letsencrypt (certbot delete removes it). The same Z also removes a legacy satellite install, the multi-region role the toolkit used before gateways (deleted in June 2026); nothing else in the menu knows that name any more.

Miners cannot connect at all (connection refused on 3333), or were dropped with "Pool paused"The stratum is paused: while paused no stratum port is open, and "Pool paused" is only sent to rigs caught in the moment the pause starts. It was paused — by you, by a scheduled window, or because the pool was just restored or migrated. Resume in Settings → Announcements → Stratum, or wait for the end time shown there
A red degraded strip on every admin page after a resumeA stratum port could not open again. EADDRNOTAVAIL on a region port means the WireGuard tunnel is not up — bring it up, then press Re-bind
"Pool manager is not running on port 8080" during step 7The service is down or still starting. Pool menu 6 to start it; journalctl -u grin-pool-manager -n 50 if it will not
"An admin already exists — registration is closed"Step 7 was already done. Sign in, or use A to reset the password
certbot failed in step 4DNS for the domain and www. does not point here yet, or port 80 is closed. The pool stays on HTTP; fix and re-run 4
403 on /admin/Your browsing IP is not in admin_allowlist (it can differ from your SSH IP). Add it and re-run 4
nginx config test failed in step 4Usually a typo in admin_allowlist spliced into an allow line. nginx keeps serving the old config. On a first run the script disables the new vhost again; on a re-run (the vhost was already enabled, the usual case when you edit the allowlist) it leaves the broken vhost enabled and says so — fix the value and re-run 4 before any reboot or nginx restart, or nginx will refuse to start and take every site on the box down
Uploaded logo or CMS images 404nginx cannot reach the app's custom_assets/ or uploads/ folder (a hand chmod, or an install from before this was fixed). Re-run 4 (or 1): both re-open the two served folders. 3 does not
A miner's Tor payout ends FailedTheir wallet's Tor listener was not reachable when the pool sent; the balance is already back on their account page, which offers Slatepack instead. Five failures in 24 hours pause Tor for that address for 24 hours
A payout stays HeldThe pool could not tell whether the send went out, so it keeps the amount locked and checks its wallet log every pass. Wait; after 24 hours an alert fires. Use Re-check on Payouts → Queue; Forced refund only when you are sure the coins did not move
Payouts show paused on every account pageThe freeze is engaged — by you, by a restore or migration, or by the alert monitor after a money check tripped. Payouts → Treasury shows the reason
Payouts froze right after I sent coins from the pool wallet by handThe ledger does not know about a raw grin-wallet send, so the wallet no longer covers what it owes. Use Operator revenue for your fee instead; reconcile on Treasury before resuming
Gateway miner shows Dead but the tunnel handshakeshub_endpoint on the gateway points at the wrong port (the node's 3416 instead of the assigned region port 3391). Paste the GRINGW1 string instead of typing values
Gateway tunnel handshakes but nothing passesAllowedIPs mismatch from a duplicate pairing. Remove the peer on the pool server (W → 4) and pair again
Gateway Status says :3333 listening but the pool's port check failsThe gateway's public stratum port was typed wrong once and stuck. Re-paste a current GRINGW1 string (it carries the port), or update the toolkit on both boxes if the gateway rejects it
A paired region does not take miners after W → 2The CLI path opens the region's listener only after a pool service restart, and you answered no. Restart the service, or pair from the admin Regions page next time
Region stays red on the connect page though the gateway is fineWildcard DNS or a stale probe; verify with nc -vz <region host> 3333. Deactivate unbuilt regions in admin Regions rather than leaving them red
Panel pairing "saves" nothing while Regions still lists fineThe service unit predates the /etc/wireguard write permission. Run pool menu 9, which replaces the unit and restarts the service; W on the CLI works meanwhile
Migrate IN stops at "old hub"The old pool still answers on its stratum port or API. Finish Migrate OUT on the old box first; nothing on the new box has started
Service refuses to start after editing the configjwt_secret missing or shorter than 32 characters — the backend fails loudly on purpose. Restore it from a backup or re-run 1
grin_wallet_dir in /opt/grin/conf/grin_pubpool.json is …, but root uses … from 9 (same for wallet_pass_file)The pool config and root's record of the wallet paths disagree, so 9 deploys nothing. The script adds "If you did not change it, treat the pool user as compromised", because that user owns the config. If you made the edit, put the value back with S, or to really move the wallet use wallet submenu 1 and type the new directory. Two harmless causes give the same message: a Z cleanup and reinstall with a custom wallet directory (Z keeps root's record while the reinstall writes the default to the config; put your directory back with S), and a wallet long kept at a path the toolkit now refuses, such as one with a space (move it to a plain path, then give that path to wallet submenu 1)
An @reboot node line still resets the secrets' group during Install or 9An old autostart line strips the node secrets' group at every boot, so the pool user cannot read them and sees the node as offline. Remove and re-add node autostart in Script 03
Settings did not load. This form cannot be saved until they do.A settings page could not read the stored settings, so its form holds defaults. Save, Restore Defaults and Save campaign stay disabled until Retry works; your stored settings are unchanged. Buttons that act at once (the draws, Run cleanup) still work and use the stored values. The Donors page's donation form behaves the same way
Alert Shares Not Recorded: share(s) accepted by the node could not be storedCritical: miners are losing credit. Check pool.db and the free space on its disk. It clears after five quiet checks
Alert Block … is on chain with a nonce this pool submittedThe node's reply to a possible block was lost, so it was not recorded. Confirm the coinbase in the pool wallet first, then see Late and lost blocks
Alert The node reported block … for a submit the pool no longer holdsThe same kind of loss, with only the hash left. Find the block on chain by that hash, then see Late and lost blocks
Alert Lost Submits Not CheckedThe chain could not be read for about an hour, so some unanswered submits were never checked. Compare the listed heights with the pool's blocks by hand
Alert Daily Giveaway StoppedThe giveaway is on but its stored rules are invalid, so no draw runs. Open Settings → Incentives and save them again, with the maximum below 60 GRIN
A giveaway draw shows On hold, or Last check … skipped appears under Recent giveaway drawsOn hold says why: the prize pool is too low or the giveaway is off, so top up or switch it on. Last check says why too: a low prize pool, a node that did not answer, or invalid saved limits. See The daily giveaway for when a skipped day is lost
A rig gets Duplicate shareThe same work, nonce and proof was already submitted. The address is not part of that check, so the same solution sent under a second address is a duplicate too. Repeats count towards the 50 rejects in a row that disconnect a rig. grin-miner draws its nonces at random so its rigs do not collide; other miner software has not been checked (read from code)
A rig gets Missing or malformed submit params or Height mismatchThe pool wants a canonical 64-bit nonce and a proof of exactly 42 ascending edges with edge bits 29–53, and the height must belong to the job named. Both count as rejects. Update the miner software, or try another (read from code)
A rig gets Share not recordedA pool database fault, not the miner's, and it does not count against the rig. See Shares Not Recorded above
